# 方案：T-0501 / T-0502 Worker RPC —— 建议废止（L2，等待评审，未实现）

日期 2026-10-13 · 作者 Claude（Sonnet 5.5） · 状态 **Proposed** · 触及：Worker RPC 协议（L2）

## 1. 任务书想要什么

常驻的 Python Worker 进程，C++ 通过 stdio 上的 RPC 协议调用它（请求/响应关联、通知回调、超时、取消、心跳、版本协商；"10 万事件无丢失无乱序；kill -9 3 秒内感知"）。

## 2. 现在实际是怎么做的（且已被真机验证）

- **每个作业一个子进程**：`JobRunner` `fork+exec` `python -m mqde.pipeline.<llm|vlm|vla|deploy>_job job.yaml --job-id ID`，独立进程组（`setpgid`），GPU 通过 `CUDA_VISIBLE_DEVICES` 隔离。
- **事件走文件**：Worker 往 `runs/<id>/events.jsonl` 追加，服务端按 `seq` tail 并以 SSE 推给前端（支持断线后 `after_seq` 补齐）。
- **取消**：向整个进程组发 SIGTERM；**崩溃感知**：`waitpid` 在 500 ms 内回收；**重试**：非零退出且非取消时指数退避重试（T-0504，有测试）。
- 本轮在 4090 上通过这条路径真实跑过 LLM / VLM / 部署评测 / 并发扫描等作业，包括失败作业（`FAILED` 与错误信息）和重复运行。

## 3. 常驻 Worker 能带来什么、要付什么

| | 收益 | 代价 |
|---|---|---|
| 模型复用 | 同一模型连续提交作业时省掉加载（0.5B：约 4–6 秒；MiniCPM-V-4.6：约 6 秒；7B 级别才明显） | 作业之间共享进程内状态：一个作业的 OOM、CUDA 错误、被 GPTQ 改过的权重会污染下一个；**FakeQuant 的 `restore()` 要求模型完全还原，这里出过 bug**（见 T-1304/T-0508 的记录），常驻会放大它 |
| 取消 | 协议级取消 | 现在杀进程组更彻底；常驻 Worker 里"取消"要靠检查点协作，卡在 CUDA kernel / 子进程（vLLM、llama-server）里的作业取消不了 |
| 崩溃隔离 | — | 现在一个作业崩溃不影响其他作业；常驻后要自己做 Worker 重启与状态恢复 |
| 实现量 | — | 新协议（L2）、版本协商、心跳、双向流控、两端各一套实现和测试；而且 vLLM / SGLang / llama.cpp 本来就是各自的子进程，Worker 并不能把它们"常驻化" |

## 4. 建议

1. **废止 T-0501 / T-0502**，把它们在任务表里标为"被文件事件协议取代（T-0504、T-0512）"。
2. 真正缺的是**契约**而不是**传输**：作业协议是 `job.yaml`（已有 `schemas/job_spec.schema.json`）+ `events.jsonl`（见 `T-0007-contracts.md` 第 2 步的 `events.schema.json`）。把这两个写成 schema 并测试，就等于把"版本协商"之外的东西都落实了。
3. 如果将来确实要省模型加载时间，更小的做法是**进程内缓存最近一次加载的模型**（同一个作业的多个配方已经是这样），而不是新建一个 RPC 层。
